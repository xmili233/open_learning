# Open Learning MVP 方案

> 状态：已确认，P0 实现中
>
> 版本：0.4
>
> 日期：2026-08-31

## 0. 建议结论

建议把 MVP 定义为：

> 一个由 Codex Voice 驱动、供 Codex 在教学过程中主动操作的实时教学画板。Codex 通过 Open Learning Plugin 中的教学 Skill 调用本机 `open-learning` CLI，在解释之前或解释过程中画出、修改、聚焦和清除教学对象，并用语音指着这些对象讲解。

MVP 不做语音、不托管模型、不做通用白板，也暂不实现 subagent。它只验证一个核心命题：

> 在相同的 Codex Voice 和相同教学策略下，让 Codex 把画板当作实时教学工具，而不是课后总结，是否能让用户更快达到可证明的理解，并且不降低延迟记忆效果？

这比“做一个 AI 教育平台”小很多，但已经包含从安装到完成一节学习的真实闭环。

## 1. 对原始设想的重新定义

### 1.1 长期愿景

尽可能提高每个人的学习效率，让更多人获得接近顶级个性化教育的学习体验。

长期产品可以组合：

- Codex 的实时语音交互；
- 共享、持续可见的视觉工作区；
- 适应用户水平的教学 Skill；
- 适合并行研究、验证和练习生成的 subagent；
- 高质量内容、来源和学习记录。

### 1.2 MVP 的中性问题

原始方案是“实时语音 + 画板 + subagent”。这些是候选机制，不是已经验证的用户需求。

MVP 真正要回答的问题是：

> 如何让一位正在使用 Codex Voice 学习复杂概念的成人，在讲解发生的当下，同时听到解释并看见 Codex 正在构建、变换和指向的外部表征，从而更快形成并验证正确的心智模型？

### 1.3 第一批目标用户

MVP 只服务：

- 已能使用 ChatGPT 桌面端 Codex Voice 的用户；
- 使用中文或英文；
- 在电脑前自主学习概念型内容；
- 愿意完成 10–20 分钟的学习和理解检查；
- 首轮试验以成人为主。

暂不把 K–12、课堂管理、考试系统、语言口语训练、多人协作纳入 MVP。

### 1.4 用户真正需要完成的任务

用户不是要“在课程结束后得到一张漂亮总结”，而是要：

1. 快速告诉 Codex 自己想学什么、已有多少基础；
2. 在听解释的同时，看见抽象对象、关系、步骤和变化；
3. 能与 Codex 共同指向同一个对象，例如“看右边这个条件”“把这里换成反例”；
4. 在追问或答错后，看见 Codex 立即修改当前表征，而不是重新输出一段长文本；
5. 暴露自己只是“听懂了”还是已经能够复述、判断和迁移。

会话结束后保留当前画面可以是有用的副产物，但它不是画板存在的主要理由，也不是 MVP 的核心使用时刻。

## 2. 需要验证的假设

| 假设 | 当前性质 | MVP 如何验证 |
| --- | --- | --- |
| 语音比打字更适合连续追问和打断 | Codex 已提供的产品能力，不由本项目验证 | 直接复用 Codex Voice，不自建语音链路 |
| 同步的视觉表征能补充语音不擅长承载的空间、关系和变化信息 | 核心产品假设 | 与相同教学策略的 Voice-only 对照比较 |
| Codex 能在恰当的教学时刻操作画板，而不是讲完后补一张图 | 关键交互假设 | 记录工具调用、画面出现和对应讲解的时间顺序 |
| 实时教学画板能提高学习效率 | 未验证，不应写成事实 | 测量达到理解标准的时间、即时成绩和 24 小时后成绩 |
| 结构化操作比生成 HTML 更快、更稳定 | 高可信工程假设 | 固定任务基准测试 payload、成功率和渲染时间 |
| Skill 能稳定引导 Codex 少说、善用画板并做理解检查 | 行为假设 | 用固定提示集和真实学习会话做 eval |
| subagent 会改善学习质量 | 未验证且不是首版必需 | MVP 不实现；主流程验证后再单独实验 |

## 3. MVP 的完整用户体验

### 3.1 首次设置

1. 用户安装并打开 Open Learning 桌面应用。
2. 应用解释：语音由 Codex 提供，本应用不录音、不运行模型。
3. 应用引导用户安装 **Open Learning Plugin**。
4. 安装桌面应用时同时安装 `open-learning` CLI；设置向导验证 Plugin 与 CLI 均可用。
5. 应用执行端到端自检：CLI 能在应用关闭时启动应用，并完成一次测试画板调用。
6. 应用提示用户在 ChatGPT 桌面端创建一个**新的 Codex Voice 任务**。

这里用户感知上可以继续称为“安装学习 Skill”，工程交付物仍是 Plugin，但 Plugin 只负责分发 Skill；桌面应用负责安装唯一的 CLI 操作面。安装、命令发现和 Voice 中的本地 shell 调用是否能在目标 Codex 环境顺畅完成，属于 P0 必须实测的产品事实。

### 3.2 一次学习会话

1. 用户打开 Open Learning，再从一个新的 Codex 任务进入 Voice。
2. 用户说：“用 Open Learning 帮我理解贝叶斯更新。”
3. Skill 最多询问两个必要问题：学习目标和当前基础。
4. Codex 打开一块空的教学工作区，根据第一个教学动作放入最少的对象。
5. 在解释一个机制之前或解释过程中，Codex 先让对应的关系、步骤或例子出现在画板上，然后用语音引用它们。
6. 随着讲解推进，Codex 聚焦当前对象，逐步揭示下一步，修改错误假设，或删除已经完成使命的临时脚手架；画面不要求不断累积。
7. 用户可以选中一个对象并追问“为什么这里成立”或“换一个反例”；Codex 通过 `read` 获取当前选择和版本，再直接修改对应对象。
8. Codex 要求用户预测下一步、比较两个对象或解决一道迁移问题，并根据回答调整画面和后续解释。
9. 会话结束时不自动生成总结图；只有当复习确有需要或用户明确要求时，Codex 才把当前工作状态整理成可回看的版本。

画板的最小教学循环是：

```text
选择下一步教学动作
  → 写入或变换最少量的画板状态
  → 用语音引用当前画面进行解释
  → 获取用户的追问、预测或作答
  → 修改、聚焦或清除画面
  → 进入下一轮
```

### 3.3 Skill 的教学行为约束

首版 Skill 应稳定执行以下规则：

- 跟随用户当前语言；中文和英文不混写，除非术语需要；
- 开始前只收集会改变教学方式的信息；
- 一次只解释一个认知单元；
- 只有视觉表征能帮助当前教学动作时才使用画板，不为“看起来丰富”而画；
- 优先先更新画面、再用语音引用它，或让画面与讲解同步出现；禁止讲完以后才补一张总结图冒充实时使用；
- 口头解释负责因果、直觉和互动，画板负责对象、空间关系、状态变化和注意焦点；两者互补，不复制逐字稿；
- 不朗读工具参数，不向用户播报“我正在添加节点”；
- 一个教学动作对应一次紧凑的批量更新，不按每句话调用工具；
- 临时例子、错误假设和中间步骤完成使命后可以修改或删除，不要求把所有内容累积成知识图谱；
- 优先通过复述、对比、预测或迁移问题检查理解；
- 不因为用户说“懂了”就标记为已掌握；
- 画板不可用时明确提示连接问题，并询问是否继续 Voice-only，不静默改变教学模式；
- MVP 中不创建 subagent。

## 4. 画板是实时教学工作区，不是总结生成器或 HTML 生成器

### 4.1 推荐决策

MVP 不允许 agent 生成 HTML、CSS、SVG 或绝对坐标，也不发明一套新的特殊 Markdown DSL。

画板同时不被定义为“课程内容自动整理器”。它首先是一块有生命周期的工作面：对象可以被加入、变换、聚焦、替换和删除。稳定的课后总结只是可能的导出形态，不应反过来限制教学过程。

原因：

- HTML/CSS 输出长，模型需要同时承担内容、布局和样式；
- 任意代码增加失败模式、渲染差异和安全风险；
- 绝对坐标会迫使 agent 反复读取和计算布局；
- 新 DSL 需要额外教学、解析、容错和版本兼容，尚无证据证明值得；
- 结构化 JSON 工具参数更容易校验、批处理、回滚和测量。

### 4.2 Agent 实际提交什么

Agent 只提交：

- 当前教学对象的语义角色、简短标题与内容；
- 对象之间的关系；
- `flow`、`compare`、`cluster` 这类有限的布局意图，而不是坐标；
- 当前需要聚焦或逐步揭示的对象；
- 需要修改、隐藏、替换、删除或清空的对象。

应用负责：

- 节点尺寸；
- 自动布局；
- 已有对象的位置稳定性，避免每次更新都让整张画面跳动；
- 配色和视觉层级；
- 连线；
- 动画；
- 缩放和平移；
- Markdown 子集和公式渲染；
- 安全清洗。

### 4.3 MVP 教学对象模型

首版只需要四类可变的教学对象：

| 类型 | 用途 |
| --- | --- |
| `concept` | 定义、机制、关键规律 |
| `example` | 例子、类比、反例 |
| `question` | 理解检查、待澄清问题 |
| `step` | 流程、推导或状态变化中的一步 |

对象正文只支持受限 CommonMark、行内/块级公式和代码片段；不支持原始 HTML。对象不是永久知识卡片：同一个对象可被更新或删除。流程、比较和概念关系由对象、边与有限布局意图表达，首版不接入 Mermaid。

### 4.4 最小 CLI interface

只暴露三个画板命令：

```text
open-learning board open '<json>'
open-learning board patch '<json>'
open-learning board read '<json>'
```

建议语义：

```json
{
  "title": "Bayesian updating",
  "language": "en",
  "objective": "Explain how evidence changes prior beliefs"
}
```

```json
{
  "session_id": "123e4567-e89b-42d3-a456-426614174000",
  "base_version": 3,
  "operations": [
    {
      "op": "put_node",
      "id": "posterior",
      "kind": "concept",
      "title": "Posterior",
      "body": "Updated belief after considering evidence."
    },
    {
      "op": "put_edge",
      "from": "prior",
      "to": "posterior",
      "label": "updated by evidence"
    },
    {
      "op": "focus",
      "ids": ["prior", "posterior"]
    }
  ],
  "layout": {
    "intent": "flow",
    "direction": "left_to_right",
    "preserve_existing": true
  }
}
```

```json
{
  "session_id": "123e4567-e89b-42d3-a456-426614174000",
  "scope": "selection_and_focus",
  "since_version": 3
}
```

`patch` 必须支持批量原子的 `put_node`、`remove_node`、`put_edge`、`remove_edge`、`focus` 和 `clear` 操作。成功时只返回紧凑结果，例如：

```json
{"ok":true,"version":4,"changed":3}
```

应用端生成稳定的视觉布局；agent 使用稳定的短 ID；增量更新不重复发送完整画板。`read` 默认只返回版本、焦点、当前选择和请求的局部对象，不把整张画板重新塞回上下文。这样减少的是“为画板服务的表达开销”，但是否减少整个 Codex 会话的输出 token 仍需测量，不能先写成结论。

## 5. 推荐技术边界

### 5.1 组件关系

```text
用户
  ↕ 语音
Codex Voice（ChatGPT 桌面端）
  ↓ 加载教学 Skill
Open Learning Plugin
  ↓ 指导 Codex 调用唯一 CLI
open-learning CLI：启动、重试、JSON 输入输出
  ↓ 认证的本机 IPC
Electron Main：校验、状态、持久化
  ↓ 收窄后的 IPC
Electron Renderer：自动布局与渲染
```

### 5.2 连接与启动方式

MVP 只暴露 `open-learning` CLI。CLI 先探测用户私有的 Unix domain socket；应用未运行时启动 Electron，并在就绪后继续原命令。保持以下约束：

- Electron 启动后创建当前用户私有的临时端点和会话凭据；
- 运行时描述文件只允许当前用户读取；
- CLI 读取描述文件后连接，不把 Electron Renderer 暴露为服务；
- 应用关闭是可恢复的正常路径，CLI 自动启动应用；启动失败返回稳定错误码；
- 不开放局域网监听，不使用固定无认证端口，不维护第二套远程 API。

P0 的目标是证明真实的 `Codex Voice → Plugin/Skill → CLI → Electron 画板` 链路。CLI 是唯一外部 interface，MCP 不作为兼容层保留。完整决策见 [`CLI_FIRST_ARCHITECTURE.md`](CLI_FIRST_ARCHITECTURE.md)。

### 5.3 Electron 安全底线

- Renderer 保持 `contextIsolation` 和 sandbox；
- Renderer 不获得 Node.js、文件系统或原始 `ipcRenderer`；
- Preload 只暴露画板需要的窄接口；
- Main 对 CLI 传入的画板参数做 schema、大小和状态版本校验；
- 禁止原始 HTML 和脚本 URL；Markdown 与公式输出必须清洗；
- 限制单节点、单批次、总节点数和边数；
- 外部链接只通过显式用户动作交给系统浏览器；
- 所有数据默认本地存储。

### 5.4 本地状态

MVP 只保存：

- 当前教学工作区状态，用于崩溃恢复和会话内继续；
- 用户明确保存的会话快照；
- 每次 board CLI 调用的时间、大小、成功或失败；
- CLI 调用、画面可见和对应语音讲解之间的时序事件；
- 本地设置与界面语言；
- 可由用户主动导出的匿名试验日志。

MVP 不保存也不处理：

- 麦克风音频；
- Codex 账号凭据；
- OpenAI API Key；
- 完整 Codex 对话记录；
- 云端用户画像。

## 6. MVP 必须包含什么

### 6.1 产品能力

- macOS 上可安装的 Electron 应用；
- 中文和英文 UI；
- 系统语言默认值与手动切换；
- Plugin / Skill / CLI 连接引导与自检；
- 一个可被 Codex 在会话过程中连续操作的单人教学工作区；
- 四类可变教学对象、带标签的有向边；
- 新增、修改、删除、清空和聚焦操作；
- 保持空间连续性的增量自动布局、缩放、平移和选择；
- Markdown 子集、公式和代码渲染；
- 三个 CLI 画板命令及严格 schema；
- 版本化、原子的增量 patch；
- 断线、应用未启动、版本冲突和非法输入的可理解错误；
- 本地会话日志导出；
- 中英文教学 Skill；
- 一组可重复执行的 Skill 和工具 eval。

### 6.2 平台范围

MVP 先发布 macOS pilot，但所有用户可见文案和内容模型从第一天支持中文与英文。

Electron 的跨平台价值保留在代码结构中；在核心假设被验证前，不同时承担 Windows、Linux 的安装、签名、权限和兼容成本。

## 7. 明确不做什么

MVP 不做：

- 自建实时语音、转写、TTS 或 Realtime API；
- 自建大模型服务或模型路由；
- Codex App Server 集成；
- subagent 创建、配置或结果面板；
- 把课程结束后的自动总结图或思维导图生成器作为核心流程；
- 让 agent 生成 HTML、CSS、SVG 或 Canvas 代码；
- 任意自由绘制、便签、套索、多人光标等通用白板功能；
- Mermaid、自定义视觉 DSL 或插件化渲染器；
- 图片生成、视频、文件附件或网页内嵌；
- 账号、订阅、云同步、分享链接或多人协作；
- 课程市场、内容库、教师后台、作业和考试系统；
- 个性化长期记忆或掌握度模型；
- Windows、Linux、移动端发布；
- 面向未成年人的专门产品承诺；
- “提高所有人学习效率”的营销结论。

## 8. 如何证明 MVP 有价值

### 8.1 主指标

**达到可证明理解的时间（Time to Demonstrated Understanding）**：

从首次解释开始，到用户在固定评分标准下同时完成以下两件事的时间：

1. 用自己的话准确解释核心机制；
2. 正确解决一个没有在讲解中原样出现的迁移问题。

“感觉懂了”“内容看起来清楚”“画板很好看”都不能作为主指标。

### 8.2 对照设计

建议进行 12–20 人的小型交叉试验：

- Control：Codex Voice + 相同教学 Skill，但禁用画板；
- Treatment：Codex Voice + 相同教学 Skill + Codex 在讲解过程中主动操作 Open Learning 画板；
- 每位用户学习两个难度相近、此前不熟悉的主题；
- 随机交换 Control / Treatment 的先后顺序；
- 使用预先定义的问题和评分 rubric；
- 记录即时理解、完成时间、24 小时后回忆和迁移表现。

只有保持 Voice、教学策略、主题难度尽可能一致，才能判断画板本身的价值。Treatment 中如果工具只在讲解结束后生成总结图，该会话不算完成实验干预，应记录为交互失败，而不是“使用过画板”。

### 8.3 Go / No-Go 阈值

MVP 建议满足以下条件才继续扩展：

| 维度 | Go 条件 |
| --- | --- |
| 学习效率 | Treatment 达到理解标准的中位时间至少缩短 20%，或在相同时间内即时成绩提高至少 15 个百分点 |
| 延迟效果 | 24 小时后成绩不比 Control 低超过 10 个百分点 |
| 可用性 | 至少 80% 的参与者无需研究人员帮助完成首次连接和一节课 |
| 主观价值 | 至少 70% 的参与者明确希望下一次继续使用画板版本 |
| 教学同步 | 抽样的视觉教学动作中，至少 90% 的画面在对应口头指代之前可见，或在首次指代后 1 秒内可见 |
| CLI 可靠性 | 有效 CLI 调用成功率至少 99%，错误能恢复且不损坏画板 |
| 本地性能 | `patch` 到可见更新的 P95 小于 500 ms |
| 协议开销 | 固定基准任务中，结构化操作 payload 明显小于等价 HTML，并且不需要布局修复回合 |

如果只提高“好看”和偏好，却没有改善理解速度或质量，应暂停功能扩张，重新检查画板是否只是装饰。

### 8.4 Token 指标的正确定位

“减少 agent token 输出”是工程目标，不是最终用户价值。它应拆成：

- 每个教学动作的 CLI JSON 参数字符数；
- 每次学习的 CLI 调用次数；
- 重试和布局修复回合数；
- 口头内容与画板内容的重复率；
- 如果 Codex 侧能取得可靠 usage，再记录完整输出 token。

首版不能仅凭 CLI payload 推断整个对话 token 已下降。画板也可能因为重复表达而增加 token，因此 Skill 必须明确“语音负责讲解与互动，画板负责可见对象、关系和变化”。

## 9. 最小实施顺序

### P0：打通一个实时教学动作闭环

目标不是做 UI，而是消除最大的未知项。

必须证明：

1. 在新的 Codex Voice 任务中能加载 Open Learning Skill；
2. Voice 任务能在解释一个概念前调用 `open` / `patch`，让画面先出现，再在语音中引用它；
3. 同一段连续教学中能至少三次修改画面，例如“加入两个对象 → 聚焦关系 → 替换为反例”，而不是最后一次性生成总结；
4. 用户中途打断或追问后，Codex 能读取当前版本并正确修改已有对象；
5. `patch` 到可见更新的延迟不会迫使 Codex 停下来等待或重复解释；
6. 中英文请求都能触发同样的教学动作循环；
7. 桌面应用 / CLI / Plugin 安装路径对 pilot 用户可执行。

只做一个窗口和最小对象渲染，但必须运行 `open`、多次 `patch` 和一次 `read`。如果 Codex Voice 只能在整段讲解完成后调用工具，P0 判定为 No-Go：这证明不了“实时教学画板”，不应继续把课后总结器包装成目标产品。

### P1：完成单节课黄金路径

- 三命令 CLI interface；
- 四类可变教学对象与边；
- 稳定的增量布局、聚焦、替换、删除和清空；
- 先画后讲或边画边讲的 Skill 教学循环；
- 中英文 UI；
- 本地保存；
- 3 个固定主题的端到端演示。

完成标准：用户只用语音，可以从空白开始完成一节有理解检查的 10–20 分钟学习；画面在教学过程中至少发生三次有教学意义的变换。课后一次性生成的总结不计入完成标准。

### P2：可靠性和试验准备

- 输入限制、安全清洗和 Electron 权限收紧；
- 版本冲突、断线和重启恢复；
- 安装自检；
- 本地事件日志与导出；
- 固定 eval 提示集；
- Control / Treatment 实验脚本与评分 rubric。

### P3：小规模 pilot

- 先做内部 3–5 人可用性测试；
- 修复连接和 CLI 可靠性问题；
- 再做 12–20 人交叉试验；
- 根据 Go / No-Go 阈值决定是否进入下一阶段。

## 10. MVP 之后的能力解锁顺序

只有前一层已经可用且有证据时，再增加下一层：

1. **实时教学画板有效**：确认教学过程中的视觉操作改善学习结果；
2. **表达类型扩展**：再评估 Mermaid、时间线、表格或图片是否填补真实缺口；
3. **学习记录**：根据真实回访需求增加复习和跨会话连续性；
4. **subagent 实验**：只用于可独立并行的资料查证、例题生成或反方验证；
5. **平台扩展**：Windows / Linux；
6. **内容与生态**：课程、教师、共享和社区。

subagent 不应因为“能力强”而默认启用。官方文档明确指出 subagent 会消耗更多 token；它只有在并行工作确实改善速度或质量时才值得加入。

## 11. 当前最大风险

### 风险 1：Codex Voice 的 CLI 调用时机不支持实时教学

官方分别提供了 Codex Voice、Plugin 和本地 shell 能力，但目标环境中的 Voice 是否会在语音讲解前或讲解过程中按 Skill 预期调用 CLI 仍需实测。即使“最终能生成节点”，如果它只能在回答结束后发生，也不满足产品定义。P0 必须先验证调用时机、连续修改、打断恢复和安装权限的完整组合。

### 风险 2：画板造成双份表达

如果 Codex 先口头完整解释，再把同样内容完整写进画板，延迟和 token 都可能上升，并退化为总结器。解决机制不是压缩 JSON 字段名，而是 Skill 约束先后顺序和内容分工。

### 风险 3：漂亮结构不等于理解

学习者可能产生熟悉感和流畅感，却不能迁移。必须把复述、迁移题和延迟测试放进产品验证。

### 风险 4：安装摩擦掩盖核心价值

如果 pilot 用户大量时间花在 App / CLI / Plugin 设置上，无法评价学习体验。安装必须是“安装 App 即获得 CLI”，并可自动自检。

### 风险 5：过早做通用白板

自由绘制、手动布局、协作和大量内容类型会迅速把项目变成另一款白板软件，却没有验证 agent 驱动学习的核心价值。

### 风险 6：增量更新破坏视觉连续性

如果每次 `patch` 都重新排列所有对象，学习者会失去空间记忆，实时画板反而增加认知负担。布局引擎必须默认保留已有对象位置，只为新增或明确重排的区域分配空间。

## 12. 请求确认的产品决策

若采用本方案，需要明确同意以下取舍：

- [x] 实时语音完全由 Codex 提供，本项目不实现语音 API。
- [x] 用户安装桌面应用即获得 CLI；Open Learning Plugin 只包含教学 Skill。
- [x] MVP 不实现 subagent，只在后续作为独立假设验证。
- [x] 画板是 Codex 在学习过程中操作的实时教学工作区，不是课后总结器。
- [x] Codex 必须能新增、修改、聚焦、替换和删除教学对象；画面不要求持续累积。
- [x] 如果 P0 只能实现讲解后的总结图，则本方向判定为 No-Go。
- [x] 画板使用保持空间连续性的增量自动布局，不是通用自由白板。
- [x] Agent 不生成 HTML / CSS / SVG，不控制绝对坐标。
- [x] 首版使用 JSON patch + 受限 Markdown / 公式，不创建自定义 DSL。
- [x] 首轮发布范围为 macOS pilot，产品语言为中文和英文。
- [x] 主指标是达到可证明理解的时间，不是使用时长或生成节点数。
- [x] 必须先完成 P0 端到端技术验证，再构建完整画板。
- [x] 通过小型对照试验后，才决定是否扩展平台和能力。
